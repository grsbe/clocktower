=== on this machine ===
# 1.
cd /d C:\Users\grsbe\Desktop\botct_webapp

# 2. build and save the image
#    scripts\build-and-export.ps1 does both of these and drops the tar in dist\
docker compose build
docker save -o dist\clocktower-latest.tar clocktower:latest

# 3 ship it
git add -A
git commit -m "..."
git push

=== on the server ===

ssh user@grsbe.de

cd /home/user/magnia/botct_webapp
git pull --ff-only
docker load -i dist/clocktower-latest.tar
docker compose up -d --no-build --force-recreate

# check it came up
docker compose ps
docker compose logs --tail=20

# check it is actually the image you just pushed, not the one from last time.
# `docker load` prints "Loaded image: clocktower:latest" -- read that line, and
# compare the id below against the one printed at the end of the local build.
docker image inspect clocktower:latest --format '{{.Id}} {{.Created}}'

# and that the container is serving that build's bundle (the hash changes every
# time the client is rebuilt)
docker compose exec clocktower wget -qO- localhost:3000/ | grep -o 'index-[^"]*\.js'
docker compose exec clocktower wget -qO- localhost:3000/healthz


=== notes ===

- The image name is clocktower:latest, set explicitly in docker-compose.yml.
  It is NOT clocktower-clocktower:latest -- compose only derives
  <project>-<service> names when the service has no `image:` key.

- git is still needed: the tar carries the built app, but docker-compose.yml
  comes from the repo. `--no-build` then makes compose run the loaded image
  instead of rebuilding from the Dockerfile.
 
- The tar travels in the repo, so it arrives with `git pull` at
  dist/clocktower-latest.tar inside /home/user/magnia/botct_webapp. Load it from
  there. Loading it by an absolute path left over from the old scp flow is how
  you end up force-recreating the container onto last week's image and seeing
  no change at all.

- Nothing is published to the host. docker-compose.yml only declares
  `expose: 3000`, so the reverse proxy reaches the container over the docker
  network.
